# ADAS Final Defense — Study Guide Pack (build plan)

## Context

The ADAS capstone final defense is upcoming. The last defense was **28 April 2026**;
roughly 1,087 commits across ~170 PRs have landed since, so large parts of the system no
longer match what the panel saw. Studying the 246-page paper and the code directly is
inefficient under time pressure, so this plan produces a **pack of ~32 study guides**
under `docs/defense/` that the team reads instead.

Each guide answers the same core questions for its topic: _what it is, where it lives in
the paper and in the code, how it was implemented, how it works, why it was done that
way,_ and ends with a compressed summary for when time runs out. They are written to be
studied, not skimmed — technical enough to survive hostile follow-ups, worded plainly
enough to actually learn from.

The guides are generated by **Luna Max in separate threads, one guide per thread**, for
concurrency. Every thread must therefore be self-sufficient: this plan supplies the
source map, the house rules, and a per-guide brief so no thread rediscovers context.

**Outcome:** the team can explain any part of the system at the level the panel probes,
with a shared cram sheet and rehearsed answers for the known soft spots.

---

## Source-of-truth precedence (applies to EVERY thread)

The most important rule here. Threads will meet repo engineering docs that frame things
differently from the paper. **That is not a contradiction to resolve, escalate, or
"correct".**

| Rank | Source                                                                          | Role                                                                                                     |
| ---- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 1    | **The defense paper**                                                           | Authoritative for all claims, framing, terminology, objectives, requirement text, figures                |
| 2    | **Test tracker + test plan**                                                    | Authoritative for all test results, measured numbers, acceptance criteria, and how a result is qualified |
| 3    | The code in this repo                                                           | Authoritative for _mechanism_ — how something actually works, file paths, line numbers                   |
| 4    | Repo engineering docs (`ai_engine/docs/**`, `paper_sync/**`, `docs/archive/**`) | Supporting context and rationale only                                                                    |

Rules that follow:

- When a repo doc and the paper/tracker differ, **the paper/tracker wins, silently.**
  Write from the paper/tracker framing. Do not add "but the code docs say…" commentary,
  do not flag it as a risk, do not hedge the paper's claim.
- Internal engineering guardrails (notes written to stop a developer doing something) are
  **not** defense positions and must never be presented as one.
- `docs/archive/**` is explicitly marked superseded. Mine it for explanatory content,
  never for current state.
- Repo docs remain valuable for _how and why_ — mechanism, rationale, engineering detail.

## House rules for every guide

1. **Terminology follows the paper.** Incidents are **Cleared**, never "Resolved".
2. **Never invent a number.** Every figure traces to the paper or the tracker. If a number
   cannot be sourced, write `[UNSOURCED — verify]` rather than guessing.
3. **Qualified results stay qualified.** If the tracker records a result as simulated,
   accelerated, archival, or scope-limited, carry that qualification through.
4. **Cite locations.** Paper references give chapter/section and table/figure number; code
   references give `path/to/file.py:123`.
5. **Plain first, technical second.** Open each mechanism in plain language, then go into
   real detail. The team must understand it _and_ defend it.
6. **Documentation only.** Never modify code — in particular never `ai_engine/adas_transfer/`
   or `ai_engine/accumulate.py`.
7. **Length:** ~300–500 lines, uniform across guides.

## Uniform guide template

```markdown
# <NN> — <Topic>

> **One-liner:** what this is, in a sentence.
> **Panel risk:** low / medium / high — and why.

## 1. What it is

Plain-language explanation. No code yet.

## 2. Where it lives

### In the paper

Chapter/section, table and figure numbers, page if known.

### In the code

File paths with line numbers, grouped by role.

## 3. How it works

The real mechanism, step by step. Sequence of events, data flow, state changes.
Include the small decisions a panelist could poke at.

## 4. Why it was built this way

The reasoning. Alternatives considered and rejected, and the evidence or constraint
that drove the choice.

## 5. What changed since the 28 April defense

What the panel last saw vs. what exists now, and why it moved. Omit if unchanged.

## 6. Limits and honest caveats

Scope limits, qualifications the tracker records, what this does not claim.

## 7. Likely panel questions

Topic-appropriate Q&A — see the guidance below.

## 8. Cram summary

The 5-minute version. Bullets. Everything essential, nothing else.
```

### Section 7 — how to choose the questions

**The question set must fit the topic; there is no fixed list.** The questions named in
the catalogue below are **seeds and minimums, not the complete set**. Every thread is
expected to add the questions its own topic naturally invites, and to drop a seed that
turns out not to fit once the material is in front of it.

Rough guidance on volume and mix:

- **Conceptual / paper topics** (objectives, RRL, methodology, definition of terms):
  ~5–8 questions, weighted to _why this choice_, _how does this compare to the
  literature_, _what would you do differently_.
- **Mechanism topics** (backup, audit, HITL, accumulation, WebSocket, snooze): ~6–10
  questions, weighted to _failure modes_ — what happens when two users act at once, when
  the process dies mid-operation, when the network drops, when the input is hostile.
- **Results topics** (Chapter 4, accuracy, performance): ~8–12 questions, weighted to
  _challenge_ — did you meet the target, why is that qualified, what does the denominator
  mean, why should we trust this number.
- **Design-decision topics** (schema growth, architecture, design decisions): ~5–8
  questions, weighted to _justification and alternatives_ — why not the simpler option,
  why did this change, what breaks without it.

Write each question the way a panelist would actually say it, including blunt or
sceptical phrasings. Answers must be **speakable in under 30 seconds** — 2–4 sentences,
not an essay. Where an answer depends on a qualification the tracker records, the
qualification goes in the spoken answer, not a footnote.
